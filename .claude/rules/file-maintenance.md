# 功能变更与文件说明

以**完整功能验收通过**为触发点。一项功能可以包含多次编辑、重试和中间提交，到验收时合并为一次后台总结。主会话完成代码、测试和功能交付后可继续下一项。文件说明作为独立的维护工作处理。

## 后台运行

1. 功能负责人在阶段日志记录功能标识和已验证的提交或提交范围。多个小修正合入同一功能批次，只有职责、关键实现发生变化的文件需要更新说明。
2. 按「功能标识 + 验收提交」去重。给只读子代理提供该版本的源码快照、涉及文件列表及预期结果，记录每个输入文件的哈希。使用后台执行（Claude Code 的 `Bash` 工具设 `run_in_background: true`），通过 `codex exec --model gpt-6.1-terra -c 'model_reasoning_effort="xhigh"'` 指定模型与档位，以有结束符的 stdin 或输入文件传递 brief。结果保存在 `.local/` 或私有临时目录。主任务照常完成，子任务退出后接收系统通知。
3. 子代理只生成文件头建议。主会话在下个合适的维护时点核对建议与源码哈希，再集中写入一次。期间有新改动的文件留给下一批，以新版本为准。已有说明准确的文件保持原样。
4. 运行失败时在日志登记「待补总结」，后续从已有批次重试。单纯的格式、注释或维护提交无需再产生总结任务。编译、测试和打包独立运行。

## 文件头格式

```ts
/**
 * @file 管理项目目录选择与绑定状态。
 * @implementation 组合目录选择和项目绑定两个 mutation，处理取消与错误并回到所选会话。
 * @updated 2026-11-20T01:55:00+08:00
 */
```

- `@file` 写清该文件对哪个功能负责。`@implementation` 用一至两句描述当前的输入、关键机制与输出，涉及跨进程、缓存、文件或权限时点出边界。
- `@updated` 填写实际功能修改时的 ISO 8601 时间及其时区。同一完整功能收尾时可以统一核对一次。避免只为刷新日期改写与本次无关的文件，历史细节由 Git 保存。
- 按源语言写注释。shebang、必须前置的版权/格式声明和编码声明保留首位，维护头紧随其后。严格 JSON、系统清单等用所属模块说明或决策记录承载。生成物和原样引入的第三方文件保留其来源和版本，维护其源文件或溯源说明。
- 集中应用说明后按需运行 `npm run check:headers`；复核完整功能范围可使用 `npm run check:headers -- --base <变更前提交>`。机械检查覆盖字段与时间格式，语义准确性仍需主会话检查。
- 可单独委派只读文件说明整理。按用户指定使用 `gpt-6.1-terra`、`xhigh`，以 `codex exec --model gpt-6.1-terra -c 'model_reasoning_effort="xhigh"'` 或能显式选择同模型及档位的工具执行，只提供本次需要的源码和范围。回传每个文件的职责、实现和依据。遇到模型不可用、降级或失败，记录实际结果。Git 与最终写入由主会话负责。
