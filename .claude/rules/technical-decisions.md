# 重要技术决策先调研、先记录、再实现

这条规则对全仓生效。遇到问题时先定位已有实现，查官方文档、维护者的示例或问题追踪，再选择验证手段。需要决定架构、引入依赖或协议、改变进程/权限/数据边界、迁移、发行策略，或者解决反复出现的故障时，在写实现代码前完成以下步骤。

1. 写出用户目标、当前失败的可观察证据、已有模块及限制。把事实、假设和仍需验证的环境条件分开。
2. 主动搜索成熟方案。优先查项目锁定版本对应的官方文档，再比较处理相同问题的开放源码项目。对重要决策尽量核对两个有代表性的实现。记录准确的 `owner/repo`、版本或提交、文件和相关函数。沿正常与失败路径读源码。若相同项目名指向多个仓库，写出实际考察的一项。
3. 比较哪部分可以原样使用、哪些做法适合借鉴，并写清差异，例如生命周期、权限撤销、数据归属、依赖与运行环境、失败恢复、维护成本与许可证。维护良好的库能覆盖需求时优先采用。对不确定的一点做最小的隔离实验，说明如何复现。
4. 在 `docs/decisions/YYYY-MM-DD-<topic>.md` 落下决策，链接到当前阶段或变更；已有相关记录则更新或另起一条取代它。记录至少包括 **问题与范围、查阅来源、候选对比、结论与理由、验证和回退条件**。没有可复用方案时，记录具体检索词/来源、被排除的方案及原因、自研的最小范围和重新评估条件。先写下选择再动手；后续实验改变结论时追加日期及证据。
5. 代码评审应能从变更追溯到该记录，区分读过源码、实际运行过和仅推断的行为。调研不替代对本项目的测试。普通样式调整、明确的小修复可在任务记录中引用已有约定，无需重复建立决策文档。

例如接入 MCP 服务，应先读 MCP SDK 文档，再查 Proma 的工具发现/连接回收，以及相近 pi-desktop 实现的授权、取消和断线处理，最后与 atelier 的项目级授权、逐次审批和跨会话使用需求对照。研究结论与外部代码引用分开记录。
