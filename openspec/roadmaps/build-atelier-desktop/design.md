# atelier 桌面版设计

## 需求与目标态

用户在本机从应用菜单打开 atelier，选一个已有项目，说「打开网页，找到资料并把结果保存下来」。右侧显示 Agent 实际操作的网页。需要登录时用户接管同一标签页，登录后交还。对话保留引用，成果能在会话里打开，也能保存到用户选择的位置。次日重开应用，历史、草稿、成果及所选项目仍可用。首站是个人 Linux 工作台，Windows、macOS 分别验收。

桌面发布验收以**安装后的应用**为对象。覆盖冷启动、离线打开历史、一次受控写入、人工接管、截图交付、关闭重开、上个版本数据迁入及回退。网关未配置时可以查看历史、配置连接、恢复草稿。付费模型调用单列证据并取得授权。

Web 作为现有入口继续维护。桌面的窗口、原生输入、文件操作和登录流程可以有独立实现。首版发布范围为 Linux 单用户本机使用；团队账号、云同步、无人值守浏览器和外部发布渠道留待相应产品决策。

## 现状与迁移范围

核对基线为 `1639970`。`desktop/main.mjs` 已有原生视图、按项目的持久分区、手动接管和部分 CDP 工具。`desktop/preload.cjs` 暴露布局、命令和状态订阅。现有宿主同时负责窗口、工具、权限、布局、子进程和退出。`server/main.ts` 从源码位置计算数据目录，使用端口和单写者锁。`package.json` 的 `desktop` 会先构建前端，然后用 `node --import tsx` 拉起服务。既有 SDK/网页实测是回归资产；安装包、跨版本迁移和崩溃恢复需要独立证据。

| 用户功能 | 桌面处理方式 | 迁移时守住的结果 |
|---|---|---|
| 窗口、项目切换、工作区布局 | 新建 desktop shell、窗口/视图生命周期和明确的宿主接口；React 聊天与列表可复用 | 原生网页、模态审批、抽屉和输入法焦点可正常切换 |
| 会话、草稿、流式消息、SDK、恢复 | 保留数据语义，抽出 RuntimeSupervisor 和运行服务；供应商调用在运行时内 | 同项目并发约束、重连顺序、草稿隔离、取消和成本记录 |
| 浏览器及人工接管 | 原生 BrowserController 独立实现 | 网页直接可点，人工输入不写入轨迹，Agent 交还后须重新观察 |
| Skill、MCP、智能体 | 保留不可变版本和授权逻辑；以运行能力契约接入桌面浏览器 | 绑定按项目/智能体和模式取交集，撤权即时生效，副作用仍逐次审批 |
| 附件、截图、HTML/PDF/Markdown 预览、交付物 | 保留不可变内容与成熟渲染器；新增桌面选择/保存/定位入口 | 粘贴和拖入均受大小/类型/归属检查；导出有明确目的地；HTML 维持隔离 |
| 安装、日志、设置、升级 | 单独建设产品包、诊断、迁移与恢复路径 | 干净环境可启动，出错时能恢复原数据或从备份启动 |

## 架构与决策

### 决策 1 · 桌面为产品入口，运行时独立承担任务

```text
可信 React 工作台 ── preload 窄接口 ── Electron main
       │                              ├─ Window / NativeFiles
       │                              ├─ BrowserController ── WebContentsView（外部网站）
       │                              └─ RuntimeSupervisor
       └─ 当前本地 API / SSE ────────────── 运行时进程
                                           ├─ SDK、工具注册、审批、停止与恢复式事件
                                           ├─ SQLite、附件与交付物（唯一写者）
                                           └─ 本机 Shunt、获准的 MCP 与隔离子进程
```

比较过扩充现有 Web 外壳、全部迁入 Electron main、独立桌面宿主加运行时三种路径。原生网页决定了桌面宿主的必要性。把持久化和模型任务搬进 main 会耦合窗口卡顿与数据库恢复。选独立宿主加运行时，代价是需要维护进程间契约和发布两种运行资源，收益是可以分别测试、取消和恢复。过渡期沿用已验证的本机 API/SSE，桌面私有控制走 IPC。独立的 Web 模式继续通过服务端能力工作。

### 决策 2 · 先打通独立发行，再扩展宿主

以 Electron Forge 的 `package` / `make` 为首选，产出 Linux x64 可解包运行的工件，并提供适配当前发行版的安装方式。发布工件随附编译后的 Node 运行时入口、兼容的 Node 可执行文件、SDK CLI、所需 worker 和前端资源。依赖 `node:sqlite`、子进程、可执行位、ASAR 外文件和许可证清单逐一做安装态验证。Node sidecar 优先于一次性切换 `utilityProcess`，便于沿用 SQLite/SDK 已验证的 Node 版本；如样包证明原生 ABI 或打包体积不合适，在 P1 记录实测和替代选择再更换。Shunt 是用户配置的服务。`bwrap` 等宿主依赖提供能力检测和修复说明。桌面启动成功与网关在线分开判定。

### 决策 3 · 控制权、网页状态与审批有单一归属

Electron main 持有项目分区、标签页及控制权。权限和当前 Run 属于运行时，每次派发前再核对。Renderer 可请求展示、导航和接管。桌面能力描述用显式 provider 标识，从现有 Playwright 配置做一次映射，替代按 CLI 路径后缀猜测实现。消息携带请求 ID、项目、标签、运行标识、超时与取消；两端运行时校验，过时响应丢弃。

可信 renderer→main 校验登记的窗口、主 frame、origin、契约版本和请求模式。外部页面使用独立 session，无工作台 preload。桌面 API 通过宿主启动握手建立实例身份，本机 Web 入口使用自身配对/授权。现有 loopback、Host、Origin 与 CSRF 检查继续用于跨站防护，P2 另验非配对客户端的敏感请求。运行时→main 使用由宿主创建的私有子进程信道，校验工具授权、项目、运行、控制代次和有效期。身份系统切换期间保留单一可信写者。

每个项目独立 profile。同项目登录态可复用，模型指定的工作标签与用户当前查看标签分别记录。接管请求使控制权进入「交接中」，冻结新指令并取消旧代次。执行端在限定时间内确认旧队列已隔离，才进入「人工控制」。已派发操作结果未知时在轨迹标明。如果执行端失联、无法确认隔离，提供重建标签入口，销毁旧目标后再允许人工输入。P4 必测导航无响应、超时、接管后迟到回包。人工态暂停观察、输入、抽取和截图；交还时清空元素引用和排队的旧指令，需重新感知页面。网站最终状态和已派发动作可能不可逆，应向用户展示「结果待确认」。超时和 Stop 应传递给实际执行端。

### 决策 4 · 数据与桌面资源各有生命周期

目标数据根使用 OS 的应用数据目录并支持显式覆盖。只读发行资源、SQLite/SDK 数据、不可变文件、Electron session 分区和可丢弃缓存分别定位。旧版 `.data/` 由独立迁移向导导入；Electron 原有 profile 的定位和命名另作清点。同一数据根只允许一个运行时写入，桌面和 Web 启动冲突显示可操作的提示。

迁移顺序为停写和关闭数据库、备份完整数据集、在副本上迁移、校验、原子切换指针。记录文件和行数、版本、哈希抽检及失败点。失败时保留旧数据根和旧版可读备份。升级后已经产生新会话或成果时，回退向导先列出新增数量和副本位置，停写并保全新版数据，支持导出新增成果。用户确认后，将旧版本指向升级前快照。旧版可见的数据截至该快照，新版产生的完整数据副本可供新版重新打开。P7 必测升级、新增消息与附件、回退、分别打开两个数据根。登录态依赖 OS 密钥环或 Chromium 格式时提供重新登录流程。日志只记录请求标识、耗时、结果码和字节数。凭据、人工输入、网页正文、图片和 session cookie 不进默认诊断包。

### 决策 5 · 以真实桌面和安装件验收

保持现有 `npm run check`、`npm test`、`npm run build`；增加桌面 main/preload 的静态检查、真正启动 Electron 的隔离测试、干净环境的安装态测试。每次用临时应用数据根、独立 `userData` 和测试项目。用本地网站、模型传输替身和 MCP 测试服务获得可重复结果。构建机桌面窗口、Wayland/X11、打包进程和 SQLite 恢复分别留证。P1 记录冷启动、内存、包体和退出的基线，并在阶段结束前冻结 Linux 首版预算。主窗口可接受输入为就绪点，以同机同数据 5 次冷启动最大值为比较口径。P2 固化启动、取消、正常退出、强制清理和崩溃恢复的时间上限及超时后的用户可见状态。P7 复用这些数字和测试环境，任何超预算项进入修复或由用户明确接受后再发布。

## 项目边界与交付物

目标职责可落在 `desktop/host`、`desktop/browser`、`desktop/preload`、`shared`、`server` 和 `frontend`；目录名留给相应变更确定。可整块替换失配的模块，依据是接口、风险、数据兼容与可复现测试。旧 `prototype/`、开发文档和已提交证据是历史资料。后续实施顺序见 [路线图](roadmap.md)，实际交付记录见 [执行日志](task-log.md)。
